# 客户分组负责人映射核验

## 适用场景

客户编码迁移时，因 `FSALDEPTID`、`FSELLER` 缺失，需要依据客户分组补齐销售归属。

## 已验证规则

- `BD_CUSTOMER.FGroup` 返回对象至少包含 `Number`、`Name`；名称要读取多语言数组中的 `Key=2052` / `Value`，不能直接对对象做 `String()`，否则会得到 `[object Object]`。
- 当分组名称确实是人员名称时，先在 `BD_SALER` 中按 `FName` 精确查询，再使用唯一匹配记录的：
  - `FNumber` → `FSELLER`
  - `FDeptID.FNumber` → `FSALDEPTID`
  - `FOperatorGroupID.FNumber` → `FSALGROUPID`
- 示例：客户 `143255` 的 `FGroup=TK03110`、名称“许远明”，对应业务员 `TK0224_GW000058_1`、部门 `BM000017`、销售组 `TK002`；单条补齐后保存回查通过。

## 明确负责人后的批量流程

当用户明确把一批客户分配给某个真实业务员时，即使这些客户原先属于“财务”等职能分组，也可以按明确指示维护负责人，但不要跳过证据链：

1. 重新读取当前客户 View 和 `BD_SALER`，按业务员姓名精确确认唯一 `FNumber`、`FDeptID`、`FOperatorGroupID` 及对应客户分组编码。
2. 用原始不可变的 FID→目标编码映射做全量 dry-run；检查待处理数量、当前旧编码、状态、目标编码占用、必填字段和跨字段归属一致性。
3. 先选一条样板实际 `Save → View`，确认 `FGroup`、`FSALDEPTID`、`FSALGROUPID`、`FSELLER` 以及编码均落库且关系一致；若样板流程包含审核状态变更，按用户意图确认是否恢复为已审核。
4. 批量写入采用逐条 `C → unAudit → View → Save → Submit → Audit → View`，任一条失败立即停止，不跨过错误继续处理；每条按 FID 回查编码、名称、组织、负责人字段和状态。
5. 只有逐条回查成功后，才从固定跳过清单移除已完成 FID；最后重新做全量目标映射、临时编码、重复编码和未完成数量核对。
6. 若用户此前说过“暂停”或“跳过”，新的明确负责人分配指示才是重新执行的授权；执行前仍必须重新读取实时状态，不能直接相信旧输出。

本次已验证的负责人映射：

```text
业务员：TK0013_GW000009_1 / 沈君梅
客户分组：TK0013 / 沈君梅
销售部门：BM000017 / 内贸部
销售组：TK006 / 营销五部
```

对于原先 `FGroup=TK0003 / 财务` 的 49 条客户，用户明确要求全部归沈君梅后，按上述映射完成补齐和改码；固定映射中的目标编码保持不变，没有重新压缩流水号。

## 必须避免

- `FGroup` 名称为“财务”等职能类别时，不能把它当作销售员，也不能假定全部客户归同一业务员。
- 同一客户分组可能出现不同销售组；例如一批客户都为 `TK0003/财务`，但现有销售组可分别为 `TK005`、`TK007`，不能据此猜销售员。
- 找不到唯一同名业务员、分组是职能类别、或销售部门/销售组不一致时，停止批量，保留原编码并取得明确映射。
- 先用一条样板执行 `Save → View` 验证客户分组未变、销售归属一致，再批量处理。
- 不要仅因脚本打印“已完成”就结束；必须重新按 FID 和固定映射做全量回查，并确认没有临时编码或重复编码。
