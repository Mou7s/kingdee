# 客户编码迁移参考

## 适用场景

客户编码规则已经调整，需要让既有客户符合新规则，同时保留原客户记录、内码和历史业务关联。此流程不适用于新建客户，也不授权任何具体账套的批量写入。

## 首选方案

1. 在 `BD_CUSTOMER` 客户列表检查当前版本是否有“批量修改/批量维护/修改编码/变更编码”。
2. 有标准操作时，先用一条低风险客户试改，再分批执行。
3. 没有批量入口时，建立专用迁移工具：查询当前客户 → 生成/读取映射 → dry-run 校验 → 用户确认 → 按客户内码逐条调用当前账套已验证的标准保存/改码服务 → 回查。

Excel 导入不能默认视为改码工具。改动 `FNumber` 后，导入程序可能仍按旧编码匹配，也可能把行当作新客户；只有在当前账套实测确认“按内码更新且不会新增”后才能使用。

## 当前账套 API 模型核对要点

`BD_CUSTOMER` 的列表查询可以返回 `FCUSTID,FNumber,FName,FDocumentStatus,FForbidStatus`，但 `DynamicFormService.View` 实测返回的是顶层 `Id`、`Number`、`Name`、`DocumentStatus`、`ForbidStatus` 等模型键。不要把列表查询的 `FCUSTID/FNumber` 直接当作保存模型字段 `FID/FNumber` 发送；批量写入前必须先读取一条真实客户的 View，确认当前账套的 Save 报文，并用一条明确的样板客户验证保存后仍保留原内码、名称和业务关联。仅看到接口返回成功，不足以证明批量迁移完成。

完整重编号时，最终编码可能暂时被本批次其他客户占用，不能按任意顺序直接改。优先使用系统标准改码服务；若必须分两阶段使用临时代码，临时代码必须先确认符合字段校验且不被外部接口使用，并在中断时保留阶段日志、停止扩散，不得留下未核对的临时编码。

## 映射表

建议字段：

```text
old_number,new_number,customer_name,fid
```

`fid` 必须来自本次实时查询；旧编码、新编码都必须保持原样，不要自动去空格、改大小写或修复看似异常的编号。客户名称只用于人工复核，不能作为唯一匹配键。

## 预检清单

- 每个旧编码只对应一个新编码；
- 新编码格式符合新规则；
- 新编码之间没有重复；
- 新编码未被迁移范围外的客户占用；
- 不存在 A→B、B→C 等临时占用冲突，或已经设计好标准改码工具支持的临时编码方案；
- 客户是否分配到多个使用组织；
- 检查销售订单、销售出库、应收、收款核销、价目表和信用资料的引用；
- 检查自定义报表、打印模板、接口和外部系统是否直接使用旧编码；
- 新规则依赖的地区、类别、等级等字段缺失时，列为人工确认，不要猜编码。

## 执行与回查

- 默认只输出预览，不写入；显式 `--apply` 才能执行；
- 按内码定位，逐条保存，记录旧值、新值、FID、响应和时间；
- 任何一条失败就停止，不跳过失败行继续批量；
- 第一条成功后重新打开/查询客户，确认 `FNumber`、名称、组织、审核/禁用状态；
- 抽查一张历史销售或应收单，确认客户仍为原记录；
- 批次完成后按 FID 回查全部结果，并保留失败清单；
- 不要直接执行 SQL 更新 `T_BD_CUSTOMER.FNUMBER`；也不要删除旧客户后重建。

## 输出要求

最终应区分：

- 已修改成功的客户数；
- 失败或待人工处理的客户及原因；
- 新编码冲突和未匹配项；
- 抽查的历史单据及关联结果；
- 外部接口仍需切换的旧编码映射。

5. **执行前逐条检查 View 返回的完整客户模型和必填基础资料引用（特别是销售部门、业务员、创建组织、使用组织等）；字段“不为空”不等于完整 Save 一定能通过，还要检查销售部门、销售组、业务员归属等跨字段一致性，并用一条代表客户做真实 Save 探测。**在本账套账套中，`FGroup` 的客户分组**只有在当前账套的分组名称确实是人员名称时**，才可按业务规则表示负责人：先读取 `FGroup.Number` 及多语言 `FGroup.Name`，确认名称不是“财务”等职能类别，再在 `BD_SALER` 中按负责人精确匹配业务员，读取该业务员的 `FNumber`、`FDeptID` 和 `FOperatorGroupID`，再将其分别作为 `FSELLER`、`FSALDEPTID`、`FSALGROUPID` 的候选值；不要仅凭名称字符串写入，也不要把客户分组编码直接当作业务员编码。**同一分组可能对应多个不同销售组，职能分组不等于负责人；若找不到唯一同名业务员，必须停下并取得明确的负责人映射，不能把分组名当销售员或按相邻客户猜填。**先用一条样板客户 Save → View 回查，确认客户分组未变、销售员/部门/销售组一致后，才扩展到批量。**若样板原本是 `D` 重新审核状态，补资料后先按用户意图决定是否恢复 `C`；改编码的标准流程通常需 `C → unAudit → Save → Submit → Audit`，不要为了改编码擅自把仍需人工复核的客户审核。**缺失或矛盾时停止并人工确认，不得按名称或相邻客户猜值，也不要借改编码擅自修正业务归属。执行后重新按 `FID` 回查 `FNumber`、客户名称、组织和状态，并抽查销售订单、出库/应收、收款核销、价目表及外部接口。标准单据通常按客户内码关联，但自定义报表、打印模板和外部系统可能直接使用旧编码，不能仅凭“保存成功”判定迁移完成。
6. 批量写入必须记录阶段并支持中断恢复：失败后先按 FID 盘点最终编码、旧编码、临时编码、`D` 状态和重复编码；不要直接重跑要求所有客户仍为旧编码的过时快照。**初次 dry-run 生成的映射是一次迁移的不可变基线：`--resume`、单条补处理和只读核对都必须加载该文件，绝不能按“当前仍为 C/A 的客户”重新生成并覆盖它。**客户反审核、跳过或补资料会改变实时状态；若据此重排内码序号，会使后续客户的目标编码整体偏移。预览输出需采用不可覆盖的版本化文件；任何意外重生成后，先从原始范围和已验证锚点（FID→目标编码）恢复映射，再继续写入。已完成最终编码且状态正常的跳过，临时编码按原 FID 续处理，反审核后保存失败且编码未改变的客户先恢复原审核状态。仅一条跳过客户补齐资料时，不要重跑全量工具：先按原始映射确认其固定目标编码、检查目标未占用和完整 View 模型，再以 FID 执行受控单条 `unAudit → Save → Submit → Audit → View`，并回查编码和状态。若 Save 返回“业务操作冲突/请稍候再使用”，立即停止：先只读核对该 FID 的编码和审核状态，再请正在编辑的用户保存或退出前端页面以释放操作锁；锁释放后重新读取完整 View 并重新做一致性预检，确认仍为原编码且状态 `C` 后才断点续跑，绝不对冲突错误盲目重试。用户明确要求跳过某些客户时，使用固定 FID 跳过名单并保留原映射编号，允许留下流水号空档；不要重新压缩编号导致已改客户再次换号。建议跳过时必须说明具体数据问题和业务含义；“跳过”不等于客户不可用。详见 `references/customers/customer-code-migration-recovery.md`、`references/customers/customer-code-migration-runtime.md`、`references/customers/customer-code-migration-stable-mapping.md` 与 `references/customers/customer-code-migration-group-owner.md`。明确负责人映射后，先用当前实时数据做全量 dry-run，再逐条执行并回查；不要因为此前曾暂停或跳过就继续沿用旧的阻塞结论。
