# 客户简称（BD_CUSTOMER.FShortName）：结构、分类与批量改写

## 简称结构（本账套现行口径）

```
<两位数字><等级字母 A/B/C/D><城市/地区拼音码><名称码>[-W]
01 C ZH LZ     → 01CZHLZ    珠海览众
02 B JS JJ     → 02BJSJJ    客户J半导体
05 C -Micron-W → 05C-Micron-W  外贸 -W
```

- 第三位是等级位（A/B/C/D），其后两位是城市/地区码（SZ 深圳、DG 东莞、ZH 珠海、XM 厦门、JS 江苏、NB 宁波…），再往后是名称码。
- **写法不统一是常态**：等级位后有空格或连字符的都有（`01A Ane-W`、`02A-Farnell-W`、`05C  CYX-W` 双空格）。改写只动开头两位，其余原样保留，不要顺手“规范化”空格/连字符。
- `-W` 后缀是外贸客户的既有习惯（见 SKILL.md「客户简称批量加后缀」）。

## 分布（实查 1038 家客户）

- 数字开头 876 家 / 非数字开头 162 家（同结构但没带前两位数字，如 `SZCJW`、`ATLANTIC-W`）/ 简称空 2 家。
- 前缀分组：`01 / 02 / 03 / 04` 四组；等级位分布 A 41 / B 138 / C 483 / D 214。
- 导出当前分布与明细：`bun scripts/tools/export_customer_shortname_digit.js`（总览 / 分类汇总 / 数字开头明细 / 非数字开头对照 四页签）。

## 前两位数字的含义：查不出对应关系，不要猜

交叉核对过，`01~05` 与以下**都对不上**：销售部门、销售员（客户分组）、城市码、结算币别、税率、客户类别、建档日期（各组都跨 2024-09-29 ~ 2026-09-16）、客户编码段（CTK/CUST 混用）、以及是否实际下过销售订单（各组绝大多数都有订单）。

结论写法：这是人工分批编号，业务含义只能问用户；报告里写成“与部门/销售员/地区/日期/编码段/订单均无对应，口径待业务确认”，不要假设成区域或业务员代码，也不要为它硬编一套解释。

## 改名规则（写操作）

- 走标准客户 Save：`C → unAudit → Save → Submit → Audit → 独立 View/executeBillQuery 回查`；View 键 `ShortName`，多语言数组按 `Key 2052` 取。锚点一律 `FCUSTID`，不用简称（简称不强制唯一，目标被占用只提示不阻断）。
- 跳过简称为空、`B` 已禁用；**`D`（重新审核）要放行**——它是上一次中途失败留下的状态，Save → 提交 → 审核即可回 `C`，把它当“状态不符”跳过反而会漏改。
- **账套给「保存」挂了合法性校验：客户简称必须以 0 开头。** 任何中间/临时前缀也必须 `0` 开头，用 `99` 会被直接拒绝（原文点名客户编码）。历史遗留的非 `0` 开头简称（`SZCJW`…）仍能存在，只拦保存。
- 反审核后必须重新 `viewBill` 取模型再 Save，必填引用（创建/使用组织、客户分组、销售部门、销售组、销售员、收款条件、结算方式）从**反审核后**的 View 取，不能用预览快照。

## 脚本（scripts/tools/）

| 脚本 | 用途 | 命令 |
|---|---|---|
| `export_customer_shortname_digit.js` | 导出数字开头客户 + 分类 | `bun scripts/tools/export_customer_shortname_digit.js` |
| `rename_customer_shortname_prefix.js` | 前缀并组 | `--from 05 --to 03 [--apply [--one <编码>]]` |
| `swap_customer_shortname_prefix.js` | 前缀对调 | `--a 02 --b 03 --temp 00 [--apply [--one <编码>]]` |
| `rename_customer_shortname_suffix.js` | 简称加后缀（`-W`） | `--suffix=-W --scope=dept` |
| `export_customer_shortname_change_log.js` | 生成修改记录 xlsx | `bun scripts/tools/export_customer_shortname_change_log.js` |

统一约定：默认 dry-run，先写预览 json + xlsx 作**不可变基线**，`--apply` 只读基线不重生；逐条守卫旧简称与状态，任一条失败立即停并写 log；已达成目标值的条直接跳过（断点续跑）。

## 前缀对调：两趟 + 借道临时前缀

- A 组 `a → temp → b`，B 组 `b → a`；一趟只能把 A 组推到临时值，**必须两趟**（脚本内 `for (const pass of [1,2])`，第二趟把临时值推到最终值）。
- 每条按**当前简称实时判定所处阶段**（原始值 / 临时值 / 最终值），已是最终值即跳过。因此中断重跑安全；不要用“当前前缀是 a 就改”的批量筛选，那会在第一趟后把已完成的 A 组和新产生的前缀混在一起。
- 临时前缀跑前先确认未被占用（`简称 like '<temp>%'` 为 0）；apply 前再查一次“非本次范围却带临时前缀”的客户，有就换前缀。

## 修改记录交付格式（用户说“修改记录发一下”时）

从各次操作的 log json + 预览基线生成**一个 xlsx**，四页签：

1. **汇总** —— 涉及客户数、操作总数、成功、失败/异常、各阶段（并组/对调）客户数与操作数、时间范围（北京时间）、当前不符预期数、改名后状态非 C / 已禁用数。
2. **客户前后对照** —— 客户编码、名称、部门、销售员、今日开始简称、现在简称、改名次数、当前状态、禁用。
3. **逐条操作明细** —— 北京时间、操作、客户编码、名称、部门、原简称、新简称、结果、备注、审核后状态。
4. **失败异常** —— **失败尝试要如实保留**（含被校验拒绝、实际未改动的那次），标明“该次尝试被拒绝（实际未改动）”，不要只留成功行。

- log 里的 `at` 是 UTC ISO，展示一律转北京时间（+8h）——用户按北京时间读。
- 客户“今日开始简称”取该客户**最早一条带原简称**的记录，失败条目（只记 error）不要当成原值，否则会写出空值。
- 生成脚本：`bun scripts/tools/export_customer_shortname_change_log.js`。

## 同时修改收款条件与补简称前缀（2026-10-14 验证）

- 用户指定的一批客户需同时改现款和简称时，先实时查询 `BD_RecCondition` 的 `FNumber,FName`，再确定目标；本次账套现款按「款到发货」（001）处理，复用前重新核对，不能假设其他账套相同。
- 将本次客户 `FCUSTID`、编码、原简称和原收款条件固化为预览基线；apply 不重新按旧条件筛选，防止漏掉已完成项或扩大范围。
- 「简称前加03C」对已有03C前缀保持原值，其余追加03C；仅在用户明确要求时采用该规则，不由收款条件自动推断简称含义。
- 按上述标准反审核、重新 View、Save、提交审核流程同时更新 `FShortName` 与 `FRECCONDITIONID`，可用这两个字段作为 UpdateFields；保存后先核对两个值，再提交审核，最后按基线全部 ID 独立列表回查状态、分组和目标值。
- 本次证据：`output/shen_cash_20261014_preview.json`、`output/shen_cash_20261014_log.json`、`output/shen_cash_20261014_verification.json`；一次性脚本 `scripts/scratch/2026-10/shen_cash.js`。范围为沈君梅分组39家月结45天客户，不能将该固定范围作为后续默认值。
