# 客户编码迁移：稳定映射与补处理

## 不可变映射

首次预览确认后，保存一份版本化映射，至少包含：

```text
fid, old_number, target_number, temporary_number, customer_name
```

目标序号只按**初始确认范围**排序一次。之后客户变为 `D`、被跳过、补齐资料或状态变化，都不得重新按当前 `C/A` 客户重排序号。

- `--resume`：只加载初始映射，以 FID 判断当前是否已达目标。
- `--apply`：禁止隐式生成或覆盖映射文件。
- dry-run：新建预览必须写到带时间戳/批次号的新路径；不得覆盖已确认的迁移基线。
- 任何覆盖事故：立刻停止写入；用初始范围、已完成客户的 FID→目标编码和至少三个已知锚点重建后，再回查后续范围。

## 只补处理一条已修正客户

适用于先前因缺客户分组、销售部门或销售员而跳过、后由用户补齐资料的客户。

1. 从原始映射按 FID 取出**固定目标编码**，不可由当前排序推算。
2. 查询客户当前 `Number`、`DocumentStatus`、`ForbidStatus`，以及目标编码是否被占用。
3. `View` 读取完整客户模型；检查创建/使用组织、客户分组、销售部门、销售组、销售员、收款条件、结算方式、名称和简称。
4. 默认 dry-run；用户已授权后：`unAudit → Save(FID + 完整模型，仅替换 FNumber) → Submit → Audit → View`。
5. 回查 FID 不变、目标编码、生效状态 `C/A`；再跑全量目标匹配、临时编码和重复编码检查。

## 同名客户

客户编码改动也可能触发同名校验。对“另一条客户不用”的说法，不能据此删除或改名：先按该客户编码/FID 查销售订单、出库、应收等历史引用。只要存在历史单据，就必须由业务方明确决定保留、改名、禁用或其他处理方式；助手不可擅自删除或改名。

## 操作锁

若 Save 报“业务操作冲突/请稍候再使用”：停止重试，先 View 核对是否已反审核且编码未改；请用户保存或关闭正在编辑的客户页面。锁释放后，恢复原审核状态（若需要），重新 View 和预检后才执行。
