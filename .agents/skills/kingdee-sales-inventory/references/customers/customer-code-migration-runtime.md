# 客户编码迁移运行时经验

## 适用范围

用于 K3 Cloud `BD_CUSTOMER` 批量改码在发生编码冲突、部分成功、主数据校验失败或用户要求跳过坏资料时的执行与恢复。

## 已验证的安全运行顺序

1. 实时读取客户列表，按 `FID/FCUSTID` 建立 `old_number,new_number,temporary_number` 映射；客户名称只用于人工复核。
2. 先用一条低风险客户验证完整 `View → 反审核 → Save → Submit → Audit → View`，确认内码、名称、组织、审核/禁用状态和历史单据关联保持不变。
3. 目标编码冲突时，找出**当前实际占用该目标编码的客户 FID**，先迁移占用者，而不是迁移准备接收该目标编码的客户。临时编码必须唯一、可回查、可恢复。
4. 每条写入后立即按 FID 回查；批量遇到任何错误立即停止，不跳过错误继续扩散。

## 部分成功后的分类与恢复

重新读取全部客户，按 FID 将映射行分类为：

- 最终编码且 `DocumentStatus=C, ForbidStatus=A`：已完成，跳过；
- 原编码：待处理；
- 临时编码：待收敛到该 FID 的最终编码；
- 原/临时编码但状态为 `D`：先判断 Save 是否实际落库；若编码未改变且只是反审核后保存失败，可只执行 `Submit → Audit` 恢复原状态；
- 其他编码或重复编码：停止，人工调查。

断点续跑不能要求所有客户仍保持预览生成时的旧编码；必须接受“旧编码 / 目标编码 / 本批次临时编码”的合法断点状态，并继续使用原 FID 映射。旧预览中的已完成客户不能重新编号。

用户要求跳过客户时，将其加入明确的 FID 跳过名单，保留原编码和用户指定的审核状态；不要重新生成压缩后的流水号，否则会让已完成客户再次换号。跳过的含义是“不纳入本批次”，不等于客户一定不可用；向用户建议跳过时必须说明具体数据问题和对业务的含义。

## Save 前置预检边界

仅检查字段是否为空不够。完整客户 Save 可能触发业务插件，对已有主数据做跨字段校验：

- `FSALDEPTID`、`FSALGROUPID`、`FSELLER` 必须同时满足当前账套的销售归属关系；
- 例如客户销售组为 `TK002`、但业务员 `BD_SALESMANENTRY.OPERATORGROUPID` 为 `TK003` 时，金蝶可能拒绝保存并提示“销售组”必填；
- 销售部门、业务员、客户分组等缺失或互相矛盾时，不要用相邻客户或名称猜值，也不要借改编码之机擅自修正业务归属；保留失败清单，人工确认或跳过；
- 预检应包含一条代表客户的真实 Save 探测，或实现与已验证插件规则等价的跨字段检查，不能只凭 View 返回“有对象”就判定可批量保存。

## 证据与输出

最终报告必须区分：最终改码数、保持原编码的跳过数、临时编码数、失败/待确认数、是否存在重复编码，以及抽查的销售订单、出库/应收单仍通过原客户 FID 关联的证据。批量脚本应保留预览、阶段日志和断点状态；不得直接 SQL 修改 `T_BD_CUSTOMER.FNUMBER`。
