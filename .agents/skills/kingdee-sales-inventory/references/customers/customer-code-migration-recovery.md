# 客户编码批量迁移：冲突与中断恢复

## 关键规则

### 1. 冲突处理对象是“旧编码的实际占用者”

目标 `new_number` 已被本批次其他客户占用时，要先通过当前快照建立：

```text
目标客户：new_number = CTK000001
占用者：old_number = CTK000001 的客户内码
```

临时迁移的是占用者，而不是目标客户。错误地把目标客户先移到临时编码，仍然会留下原占用者，最终 Save 依旧报“组织内编码唯一”。处理前必须确认：

- 目标编码未被批次外客户占用；
- 批次内占用者全部列出并去重；
- 临时编码逐一绑定到实际占用者的 FID；
- 临时阶段完成后再写最终编码。

### 2. 不要用旧的全量快照直接重跑

批量写入可能在任意一条失败后留下混合状态：

- 已完成最终编码且为 `C`；
- 仍保留旧编码且为 `C`；
- 已迁移到临时编码且为 `C`；
- 反审核后保存失败，旧编码仍在但状态为 `D`。

失败后先只读按 FID 盘点全部迁移对象，统计最终、旧编码、临时编码、异常状态和重复编码。不要直接重跑只接受“全部仍等于 old_number”的 apply 脚本。

恢复顺序：

1. 对只改了临时编码的客户恢复原编码和原审核状态，或明确记录其临时状态；
2. 对反审核后保存失败的 `D` 客户，保持编码不变，只恢复为已审核；
3. 重新生成实时映射；
4. 使用断点续跑逻辑：最终编码且状态正常的跳过，旧编码待处理，临时编码按其 FID 继续，其他状态停止并人工确认。

每个恢复动作都要先校验当前编码、FID、状态和禁用状态，不得依据旧日志盲改。

### 3. Save 前验证完整客户模型

客户编码改动不能只发送 `FCUSTID + FNumber`。当前账套实测需要从 `DynamicFormService.View` 读取并保留客户名称、组织、客户分组、结算条件、结算方式以及已存在的相关基础资料引用，再只替换 `FNumber`。

批量前应对每条客户检查必要字段，例如 `FSALDEPTID`、`FSELLER`、`FCreateOrgId`、`FUseOrgId` 等。若 View 中缺失必填引用：

- 不要使用相邻客户或名称推测；
- 不要跳过失败客户继续批量；
- 记录客户 FID、编码、名称和缺失字段；
- 先恢复因反审核产生的 `D` 状态；
- 补齐经过业务确认的字段后重新生成/续跑映射。

### 4. 单据关联与外部引用

保留原客户内码时，标准销售订单、销售出库、应收、收款等按客户内码关联的历史关系通常仍指向同一客户；回查时至少抽查一张历史销售/出库/应收记录。另一方面，自定义报表、打印模板、Excel 和外部接口可能直接保存客户编码，须单独检查旧编码引用。

### 5. 可核对的执行记录

每条记录至少保留：`FID`、旧编码、临时编码（如有）、最终编码、客户名称、执行阶段、Save/Submit/Audit 结果和最终 View 状态。批次完成后核对：

- 最终编码数量；
- 旧编码和临时编码残留；
- `C/A` 状态；
- 重复编码；
- 失败/待人工客户；
- 抽查的标准单据关联。
