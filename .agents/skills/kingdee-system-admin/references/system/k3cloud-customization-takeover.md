# 金蝶云星空二开接管（原开发者联系不上时）

用途：接手一个「二开由前任 IT 安排外部做的、人已离职」的账套。目标是把**范围、代码位置、处置手段、补丁影响面**自己摸出来，而不是等原开发者。结论要能支撑「能不能打补丁」和「打坏了怎么办」。

## 1. 定范围：只认元数据里的二开标记

- 对象都在 `T_META_OBJECTTYPE`：`FID` 是 GUID（而非 `SFC_OperationReport` 这类标准 FormId）且 `FINHERITPATH` / `FBASEOBJECTID` 指向标准单据 ⇒ 该单据的**二开扩展**；`FSUPPLIERNAME` 存二开方代号（如 `UNW` / `ZBMY`），金蝶自带对象一般填 `Kingdee`。用 `FBASEOBJECTID` 反查可以知道每个扩展对象扩展自哪张标准单据。
- `FSUPPLIERNAME` 里会混进脏值（本环境出现过手机号、`1` 这类），**不能拿它当唯一筛选条件**；先按「GUID FID ＋ 有继承路径」取扩展对象，再用 `FSUPPLIERNAME` 归到哪家二开方。
- 结论按「面 vs 深」表达：实测是 **232 个扩展对象 / 103 张单据，但真正含自定义代码的只有 9 处**。这个对比才是判断补丁风险的关键，只说「二开很多」没有信息量。
- 数据库侧的二开痕迹还有 `Z_` 前缀表（与 `T_` 表并存，本环境 1751 张），抽样往往能看到标准表的镜像。

## 2. 代码在哪：插件注册与脚本源码都在元数据里

- 元数据 XML 里能看到该单据的全部插件注册（`<PlugIn>` 节点、`IsEnabled`）；金蝶的**「Python 脚本」插件源码原样存在元数据里，可读可改，不依赖原开发者** —— 这是「人走了也能接手」的根本原因，要作为首要结论告诉用户。
- 三类要分开报：① Python 脚本插件（源码在手，风险最低）；② 编译好的 C# 插件（形如 `wfs.BL` / `KDYF.*`，无源码，必须单独从 `WebSite\bin` 拷一份留底）；③ 报表插件（自建报表对象上常见）。
- 一把导出脚本是坑：元数据里带 Python 脚本的对象可达上百个，**绝大多数是金蝶自带示例**。只导 §1 圈定的二开对象，否则 `output/` 会被上百个无关脚本淹没、还得回头清理。
- 插件注册里留意**仍处于启用状态的调试脚本**（脚本名就叫 `123` / `test`）。它们不属于本次故障，但补丁后这些单据一旦报错，第一嫌疑就是它们——写进清单让用户确认能否停用。

## 3. 处置手段：不改 dll 就能止损

- 出问题的第一动作是在元数据里把该插件注册置为**禁用**，**保留 dll 与元数据不删**：业务立刻能继续跑，Python 脚本还能直接改源码。因此排查顺序是「从报错信息认出插件名（`wfs` / `KDYF` / 脚本中文名）→ 禁用该注册 → 修好再启用」。
- **继承金蝶标准类的报表/服务插件是升级敏感度最高的一类**：父类成员签名一变就是 `MissingMethodException`/`TypeLoadException`；同族多版本并存时先切回旧版本或标准报表顶上。
- 找源头：`ManageSite\App_Data\ISVConfigure.xml` 的 `Name` / `DevCode`（如 `UNW`）＋ dll 的编译信息（Company/Product），报给金蝶客服/客户经理可查是哪家伙伴部署的。这是唯一需要走外部渠道的事，越早问越好。

## 4. 写进补丁执行单的形态

清单按「对象 → 扩展自哪张单据 → 插件 → 类型 → 启用状态 → 补丁后怎么验证 → 出问题怎么禁用」列；再给一段验证顺序（先测带插件的那几张单据，再测报表与 PDA/条码之类外设对象）。**编译型插件（无源码）是唯一必须提前找原厂/实施确认的部分**，Python 脚本与元数据扩展都能自行验证 —— 把这个边界说清楚，不要把「二开要重新编译」当默认结论吓住用户，更不要因为「二开没人维护」就建议推迟补丁。
