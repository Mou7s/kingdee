# K3 数据权限的基础资料联动边界

## 结论

不要把“客户基础资料设置了数据规则”理解成所有销售单据和报表都会自动继承。金蝶官方手册（[数据权限](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E6%95%B0%E6%8D%AE%E6%9D%83%E9%99%90)）的关键规则是：

1. 数据规则默认只对单一对象有效；业务单据查看使用该业务单据查看权限上的数据范围。
2. 基础资料数据范围通常首先影响单据新增时的 F8 选择。
3. V7.7 以后，只有开启“基础资料数据范围联动应用到业务对象”，并配置基础资料对应的业务对象及受控字段，才会把基础资料范围联动到业务单据列表。
4. 报表可受“报表的基础资料数据权限由报表本身的基础资料数据范围控制”选项影响，不能用业务单据的结论替代报表验证。
5. 角色权限按并集检查：同一业务对象若有角色授予查看且没有 `FDATARULE`，个人角色上的“只看自己”不能可靠地收窄最终范围。

## 只读排查顺序

1. 从页面菜单或接口确认真实对象，不要只看中文名称：常见需分开的对象包括 `BD_Customer`、`SAL_SaleOrder`、`AR_RECEIVEBILL`、`AR_SumReport`。
2. 查账号、全部角色及员工/业务员绑定。`T_SEC_USER`、`T_SEC_ROLEUSER`/`T_SEC_USERROLEMAP`、`T_BD_OPERATORENTRY`、`T_BD_STAFF` 是常见入口；不要只查一个“个人”角色。
3. 对每个对象查角色的查看权限和 `FDATARULE`：`T_SEC_FUNCPERMISSION` + `T_SEC_FUNCPERMISSIONENTRY`，权限项通常通过 `T_SEC_PERMISSIONITEM` / `_L` 解释为“查看”。
4. 用 `FDATARULE` 回查 `T_SEC_DATARULE` / `_L`，确认规则的 `FOBJECTTYPEID`、过滤字段和变量，不能只看规则名称。
5. 报表额外查 `T_BAS_RPTDATARULECONFIG` 是否有该报表与 `BD_Customer` 的映射；没有映射时，不要宣称客户基础资料规则会联动到该报表。
6. 选一条客户主数据上销售员明确是其他人的样本，沿 `T_BD_CUSTOMER.FSELLER` 及员工/业务员表核对，再到页面实际验证。

## 解释“销售订单没设规则但看起来正常”

这不是基础资料规则必然继承的证据，至少可能是：

- 已开启全局基础资料联动，且销售订单已配置客户受控字段；
- 销售订单列表使用内置的业务员/组织隔离逻辑；
- 用户使用了默认查询方案或只测试了自己负责的客户；
- 实际受限的是客户 F8 选择，而不是销售订单列表查看。

因此要分别验证 `SAL_SaleOrder`、`AR_RECEIVEBILL` 和报表对象，不能用“销售订单正常”推导“应收报表也正常”。

## 自建页面边界

若页面由 ctk-system 等自建服务直接查 K3 SQL，金蝶原生数据权限不会自动执行。接口的登录/功能权限只保护入口；列表和明细必须在服务端根据当前会话解析出的业务员/客户范围过滤。前端关键词筛选、隐藏菜单或只给 `BD_Customer` 菜单加权限都不能作为数据隔离。

## 输出格式

报告至少分为：

- 已验证：账号、角色、对象、查看权限、数据规则、员工/业务员绑定、样本客户；
- 规则解释：是否启用联动、是否配置受控对象、报表是否单独控制；
- 可能放大范围的角色或接口；
- 未验证限制：页面真实对象、全局选项或缓存状态；
- 建议修复：移除不需要的宽权限，或在每个实际对象/报表配置明确规则；修改后退出重登并用“自己客户 + 他人客户”各测一条。

所有查询默认只读；不要直接 SQL 修改权限或业务数据。
