# 从包装入库汇报补做测试/分选汇报

适用于：工序计划中的“测试分选”当前无汇报或台账为 0，但后续“包装入库”已有已审核汇报，需要按包装实际汇报数量补做测试汇报。

## 1. 先做当前状态预检

不要使用旧 JSON 或旧 FID 直接写入。按明确的计划号集合重新查询：

- `SFC_OperationPlanning`：`FID`、`FBillNo`、`FOperNumber`、工序名、`FReportQty`、`FQualifiedQty`、状态。
- `SFC_OperationReport`：按精确 `FSourceBillNo` 查询所有状态，不只查 `C`。
- 测试/分选必须按计划的真实工序号匹配；同一张汇报单可能有多个来源计划。
- 包装数量取对应计划、对应包装工序号的已审核汇报分录 `FQuaQty` 合计，而不是整张包装汇报单的表头数量。
- 目标数量应与包装计划台账 `FReportQty/FQualifiedQty` 一致；不一致时停止并报告差异。
- 测试无汇报时才补做；已有 `C` 且 `FQuaQty/FFinishQty` 已等于目标的跳过；已有 `A/Z` 草稿可续处理，不要再次 Push。

## 2. 计划分录绑定

通过 `DynamicFormService.View` 读取当前工序计划，在 `Entity[].SubEntity[]` 中按工序号和工序名找到测试分选分录。汇报模型的 `FOptPlanOptId` 使用该 `SubEntity[].Id`，不能使用整张工序计划的 `FID`。

## 3. Push 的实际行为

`DynamicFormService.Push` 从一张工序计划下推到 `SFC_OperationReport` 时，可能返回多张按工序拆分的草稿（实测一张计划可返回 6 张：固晶、焊线、模压、切筋、测试、包装），不能写成“返回 1 张”的假设。

处理顺序：

1. 对 `SuccessEntitys` 的每个 FID 逐一 `View`。
2. 必须确认草稿所有分录的来源计划号是目标计划。
3. 按来源计划号 + 工序名 + 工序号找到唯一测试草稿。
4. 只删除本次 Push 产生的其他空草稿；不要按计划号把已有已审核汇报一起删除。
5. 测试草稿默认数量可能是计划基数（例如计划基数 13.44），不是包装汇报数量（例如 12.5），必须显式覆盖。

## 4. 保存测试草稿

新建/续处理的测试草稿只保留目标测试分录，使用 `FEntity` 保存；数量字段按实际表单字段明确填写：

- `FQuaQty = 目标包装汇报数量`
- `FFinishQty = 目标包装汇报数量`
- `FBaseQuaQty = 目标包装汇报数量`
- `FBaseFinishQty = 目标包装汇报数量`
- `FPrdQuaQty = 目标包装汇报数量`
- `FPrdFinishQty = 目标包装汇报数量`

同时保留/填写 `FSourceBillNo`、`FOperNumber`、`FProcessId`、`FWorkCenterId`、`FDeptID`，以及正确的 `FOptPlanOptId`。保存时使用 `IsDeleteEntry: true`，这样新下推草稿中的其他工序行不会残留到测试汇报。

## 5. 提交、审核与断点续跑

每个计划单独按以下顺序执行并记录新 FID/单号：

1. Push（没有可用草稿时）
2. View 验证来源和目标分录唯一
3. 删除本次生成的非目标空草稿
4. Save
5. `submitBill("SFC_OperationReport", [fid])`
6. `auditBill("SFC_OperationReport", [fid])`
7. 立即重新查询该计划的测试汇报和计划台账

批量执行必须顺序化或有明确的断点记录。若命令超时，不要重新运行整批：先重新查询所有目标计划的 `C/A/Z` 状态，`C` 且数量正确的跳过，`A/Z` 的目标草稿续处理，其余才重新 Push。失败或部分成功时停止扩散。

## 6. 最终验收

按原计划号集合重新查询并逐条核对：

- 测试分选汇报恰有目标汇报，状态为 `C`。
- `FQuaQty`、`FFinishQty` 与包装已审核汇报分录合计相等。
- 测试分选工序计划 `FReportQty/FQualifiedQty` 已更新并与目标一致。
- 没有遗留本次 Push 产生的非目标 `A/Z` 空草稿。
- 包装入库及其他已有工序汇报未被修改。

此流程仅适用于工序汇报补做，不适用于 AP_PAYABLE；不得借此流程提交或审核财务应付单。
