# 工序汇报删除追踪要点

用于追查某个 `SFC_OperationReport` 是否被人工删除、删除人/时间、以及它是否属于指定工序计划。

## 只读调查顺序

1. **先查当前业务数据**
   - 按 `FSourceBillNo=<工序计划号>` 查询 `SFC_OperationReport`。
   - 带分录字段时按 `FBillNo` 去重统计“汇报单数量”，按 `FEntryID`/真实主键统计“分录数量”；不能把 API 返回行数直接当单据数。
   - 同时查 `SFC_OperationPlanning` 的目标工序行：`FReportQty`、`FQualifiedQty`、`FOperStatus`。

2. **操作日志查现表和备份表**
   - 本账套删除追踪的主要日志表是 `T_BAS_OPERATELOGBK`；`T_BAS_OPERATELOG` 查不到不等于没有日志。
   - 筛选 `FOBJECTTYPEID='SFC_OperationReport'`，重点看 `FOPERATENAME` 为“反审核”“删除”“保存”“提交”“审核”的记录。
   - 删除通常有两条日志：
     - “操作执行过程，调用删除操作：关联的单据内码:<FID>”；
     - “单据编号为<单号>的工序汇报，删除成功！”。
   - 用 `FINTERID` 将同一张单据的保存/审核/反审核/删除日志串起来；再用 `T_SEC_USER.FUSERID` 查 `FNAME` 和 `FUSERACCOUNT`。
   - 同步保留 `FCLIENTTYPE`、`FIPADDRESS` 作为审计线索，但不要把机器/IP直接当作业务原因。

3. **确认源计划，禁止凭单号顺序认定**
   - 单据物理删除后，删除成功日志通常只保留单号和 FID，不保留 `FSourceBillNo`、工序号或分录内容。
   - 必须优先用删除前的日志、已存在的转移单、`FOPTPLANNO`/`FOPTPLANID` 等业务关联交叉核对。
   - “单号刚好夹在两个已知单号之间”、同一操作员、同一天等只能作为候选线索，不能当作源计划已验证事实。
   - 若直接源关联缺失，应分别写明“已验证的删除记录”和“最吻合候选/推断”。

4. **确认删除前动作和下游影响**
   - 重点判断是否存在“保存→提交→审核→反审核→删除”的人工修正链；这只能说明删除方式和时序，不能自动证明删除原因。
   - 对目标计划重新查上下游 `SFC_OPERATIONTRANSFER`：上游转入仍在、下游转出缺失，是“汇报删除后未继续流转”的支持证据，但仍不能代替报表源字段。
   - 必要时查结算和入库；不得因为没有汇报单就断言外发工序未完成。

## 删除后的可验证边界

- 批量清理重复汇报前，逐张 `View` 核对 `DocumentStatus`、`CancelStatus`、所有 `OptRptEntry`，按 `OptPlanOptId` 对上保留的已审核非作废汇报，不能只按工序名称或单号相近判重；跨多计划的汇报单须核对全分录。
- 本账套实测：作废汇报调用 `Delete` 返回“作废数据不允许删除”，即使单据状态为 `D` 也不能直接删除。首错停止批次；用户另行要求仅删除非作废记录时，排除作废单和已删除单后重新预检，不自动反作废。
- 非作废 `A/D` 重复汇报删除后，计划 `ReportQty` 可同步扣减，`QualifiedQty` 保持已审核汇报口径。必须逐单查无，并复查计划数量、保留单状态与全分录数量，不能只凭删除接口成功宣告完成。

- 删除成功后，`T_SFC_OPTRPT` 和 `T_SFC_OPTRPTENTRY` 可能都查不到；这只能证明当前表没有数据，不能恢复删除前的分录数量。
- 操作日志一般不记录报表分录条数。回答“有多少个工序汇报”时必须先区分：
  - 单据数量：例如某个单号本身是 1 张单；
  - 分录数量：删除后若没有快照/审计明细，报告“无法从当前库确认”，不要把 0 当作删除前数量。
- 数据库驱动返回的 `datetime` 可能以带 `Z` 的字符串序列化；报告时保留数据库原始值，并明确是否做过时区换算，不要无依据转换成本地时间。

## 回复要求

按“已验证事实 / 推断 / 未验证限制”分栏或分段。明确列出单号、FID、操作人账号、反审核时间、删除时间、当前是否仍存在、关联上下游，以及本次是否只读。发现候选单号误归属时，应主动纠正，不要沿用早先的错误关联。
