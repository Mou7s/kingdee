# 生产订单碎片化诊断（MO260710048 案例）

## 现象
- `MO260710048`（FID 122457）在 `T_PRD_MOENTRY` 有 14 行：`FENTRYID 246269(13.8K)+249326-249338(各19.2K)`，合计 `263.4K`（`F_UNW_QTY_H1G`/`F_CEFX_NUMBER`），每行 `F_GONGXUHAO=TX087471-484`。
- `T_SFC_OPERPLANNING` 14 张（FID 240707-240720）`FMONUMBER=MO260710048`，`FMOENTRYID` 一一对应 `T_PRD_MOENTRY.FENTRYID`，`FMOQTY` 13.8/19.2 对齐。
- 每张 TX 下 `T_SFC_OPERPLANNINGDETAIL` 各 11 道工序（`FOPERNUMBER 10-110`），`FOPERQTY=129.6`，`FOPERSTATUS=4` 开工，`B` 表 `FREPORTQTY=0` 未汇报。

## 是否异常的判断
- 本账套多行是**常态且合规**：`MO260710048` 14 行、`MO260901013` 52 行，`F_GONGXUHAO=TX号`、`FMOENTRYID` 一一对应 `SFC_OperationPlanning` 是本账套按晶圆 lot 拆分的正常模式；`MO260901022` 单行（15000）是另一类产品形态，不能以行数判错。用户已确认 14 行、TX 号、K 数拆分正确。
- 需对比同类订单：生产模式为按晶圆 lot 拆分的会多行；单行订单如 `CTK10` 成品仓 `15000 K` 则单行。核对 `T_SAL_ORDER(FID 143259, XSDD032981)` 源头 `FQTY` 是否等于 `SUM(T_PRD_MOENTRY.FQTY)`。
- `FOPERQTY` 与 `FMOQTY` 口径不同（工序计划台账基数 vs MO K 数），`129.6 vs 19.2` 的 6.75 倍差不直接代表错误；应看 `FOPERQTY` 是否在同订单内一致（本单全 129.6 一致）及与 `B` 表汇报量是否匹配。

## 诊断 SQL
```sql
-- MO 分录
SELECT FENTRYID, FSEQ, FQTY, F_GONGXUHAO, FROWID FROM T_PRD_MOENTRY WHERE FID=122457 ORDER BY FSEQ;
-- 工序计划头
SELECT FID, FBILLNO, FMOENTRYID, FMOQTY FROM T_SFC_OPERPLANNING WHERE FMONUMBER='MO260710048' ORDER BY FBILLNO;
-- 工序明细（注意 DETAIL 无 FID，用 FENTRYID）
SELECT d.FENTRYID, d.FDETAILID, d.FSEQ, d.FOPERNUMBER, d.FOPERQTY, b.FREPORTQTY, b.FQUALIFIEDQTY
FROM T_SFC_OPERPLANNINGDETAIL d LEFT JOIN T_SFC_OPERPLANNINGDETAIL_B b ON d.FDETAILID=b.FDETAILID
WHERE d.FENTRYID IN (SELECT FID FROM T_SFC_OPERPLANNING WHERE FMONUMBER='MO260710048');
```

## 坑位
- `executeBillQuery` 带分录字段会按分录返回多行，统计单据/分录需按 `FID`/`FENTRYID` 去重；`TopRowCount` 默认 10 会截断（本单首次只查到 10 张 TX）。
- `T_SFC_OPERPLANNINGDETAIL` 列名为 `FENTRYID/FDETAILID`，无 `FID`；`T_SAL_ORDERENTRY.FQTY` 为 `DECIMAL(23,10)`，无效列如 `FBASEQTY/FAMOUNT` 会报 207。
- 恢复链（2026-08-20 管理员A/TK2869 重建）为 API 逐 TX 拆 MO 分录，需核对销售订单 `214175` 行总量与 `FROWID` 同源（`f4ee0831-...`）一致性。

## 与 TopRowCount 的关联
首次 `bun run search-bill -- MO260710048` 仅显示 10 张 TX，误判为 10 张；放大 `TopRowCount=20` 并查 DB 才确认 14 张。任何数量核对前先放大查询并按 FID 去重。
