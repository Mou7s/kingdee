## 输入工作簿

1. 保留原始 `.xls`，用 LibreOffice 转为临时 `.xlsx`；`openpyxl` 不直接读取旧 `.xls`。
2. 用 `openpyxl` 按精确 sheet 名选择业务明细，不按 sheet 序号猜。旧表的前几行可能是合并标题和空白行，先定位表头再定位数据起始行。
3. 删除非明细 sheet 后重新加载，确认 `workbook.sheetnames` 只有目标表，并回读列数、表头和前几条明细。
4. 公式列区分公式文本与缓存值。`openpyxl` 保存后 `data_only=True` 可能返回空缓存；dry-run 需要按公式复算并注明，不能把空缓存当零金额。

## TX 映射与单价分批

- 先统计单价去重值、每种单价行数、明细数量和金额。
- 对账单里的 `TX074145-0-60` 只作为候选值；先用当前 `SFC_OPERPROCBALANCE.FOPNo` 验证是否对应 `TX074145`，不能凭字符串截断直接当主键。
- 金蝶初筛可按供应商、单价和期间查询；对没有命中的 TX，必须再按候选 TX 查询全单价/全日期，区分真正无记录和已有其他单价记录。

## AP 查询金额陷阱

`AP_PAYABLE` 的 `executeBillQuery` 带分录字段时，表头金额字段可能随每个分录重复返回。禁止直接逐行累加 `FALLAMOUNTFOR`、`FNOTAXAMOUNTFOR` 或 `FTAXAMOUNTFOR`。

可靠做法：

1. 按真实 `FID`/`FEntryID` 去重；统计单据数按 `FBillNo` 去重。
2. 对候选 AP 调用 `viewBill("AP_PAYABLE", fid)`，读取 `AP_PAYABLEENTRY` 的真实分录金额、数量、单价、状态、日期和来源单号。
3. dry-run 汇总可用分录 `FPRICEQTY × FTAXPRICE` 复算，但明确标记为复算金额，不冒充表头金额。
4. 同一 TX 多张 AP 必须展开逐张分录，判断“拆分”还是“旧 AP + 新 AP 重复”；未确认前不删除、不合并、不把旧新简单相加。

本账套 `AP_PAYABLE.View` 实测可能不返回表头 `DocumentStatus`。单据状态应以同一轮实时 `executeBillQuery` 的 `FDocumentStatus` 为准；`View` 继续核对 `CancelStatus`、`SourceBillType` 与实际 `AP_PAYABLEENTRY` 分录。不要把 View 中缺少状态字段当成草稿，也不要因此跳过状态回查。

## 差异排查顺序与金额精度

排除旧账后问“与这张财务应付对上了吗”，必须以该财务单实际分录集合逐计划比较，不能只用全范围均有应付或下推完整性代替金额一致。2026-10-23 外协厂X核验：按用户确认排除TX085197、TX0900800时，0.667组只减TX085197的78.039元（后者对账价0.8，本组无该行；另4片亦不在源表），61305.304−78.039=61227.265元；AP00165011实存61113.20元，差114.065元。对账仍有未入本张的TX085171（79.373元，已关联旧财务应付），剩余同集合对账61147.892元，与本张尚差34.692元，其中17计划数量不同净差34.031元，其余等量计划分位金额差净0.661元。证据 `output/xinyang-ap00165011/0667-amount-comparison.json`。已下推只证明存在财务单，不单独证明已在以前对账或应排除；排除必须以用户确认的业务期间/已结账事实为依据，不擅自进一步排除TX085171或改单价。

用户明确筛选的是暂估应付时，单独查询 `FSETACCOUNTTYPE=2`，不能继续用“财务优先”的集合解释前端条数；用户说筛选明细行数时，也不能自行改解为去重计划数。2026-10-23 追加核验：本次对账计划范围的暂估0.667（按6位显示）为766分录、765计划，TX085197分为AP00157329的117片和AP00157779的4片；暂估TX085171实际价0.5900000027，不在0.667组。交付去重工作簿重新读取为766条0.667原始明细；若用户当前副本显示765条，应取得当前文件/连接会话的行级证据后做差集，不断言就是计划数差。证据 `output/xinyang-20261023-price-update/0667-temporary-count-live.json`。

按单价筛选比较条数时，分别统计原始明细行数、去重计划数和当前应付分录数，并比较计划集合。计数相等不证明逐行相同：对账多行可对应一笔应付，一计划也可有不同来源的多笔应付。2026-10-23 外协厂X0.667实时核对：交付去重明细766行、765计划（TX0908440两行）；按“有财务优先财务，否则暂估”取当前应付亦为766行、765计划（TX085197为117片和4片两笔）。计划集合仍不同：金蝶0.667组含对账价0.8的TX0900800，对账0.667组含金蝶价0.661442的TX085171。证据 `output/xinyang-20261023-price-update/0667-count-live.json`；前端表单和筛选条件未提供时，不宣称该结果等于用户前端的筛选集合。

- 对账以工序计划号逐条匹配自己的含税单价和金额；不得用全单总额/总数量反推一个统一单价，也不得把所有计划的单价一起改成平均值。
- 通常按以下顺序查：先看每个工序计划的含税单价是否不符；再看条数/数量是否不符；最后查明细行缺失。缺行常见原因包括没有做委外、委外结算发错供应商。缺行调查要展开上下游单据确认，不能只按“无 AP”下结论。
- 用户限定为“逐行金额核对、不改数量”时，照该范围比较每个计划的金额；把数量差独立标出，不擅自改数量。若要改价，也按计划号单独核价，不用总额差反推全单统一价。
- 用户明确要求“数量不动、每个工序计划金额各自对上”时，按计划号汇总对账金额，以金蝶当前该计划数量为分母，逐计划计算建议含税价：`round6(该计划对账金额按分取整 ÷ 金蝶当前数量)`。目标金额是该计划对账明细合计按分取整；只改数量不一致且用户要求调价的计划，其他计划保持原价。输出时标注这是为匹配现有数量计算的“调平价”，不是合同真实单价。
- 不能只用除法结果承诺金蝶金额必然相等。先用当前 AP 的数量、含税单价、税率和金额验证该账套/单据的舍入模型；本次实测的 13% 税率分录可用：含税单价除以 `(1 + 税率)` 后保留 6 位作为未税单价，未税金额按未舍入的 `数量 × 未税单价` 取分，税额按未舍入未税金额乘税率取分，含税金额为两项之和。逐条回算必须与当前 AP 金额吻合后，再验证建议价能否落到计划目标金额；若无法精确匹配，报告可实现的金额和舍入差，不改数量或擅改税额。
- 比较金额前先统一精度口径：对账表可能保存含税单价×数量的三位小数明细并直接汇总；金蝶 AP 可能按未税单价计算未税金额、单独计算税额，各金额分别舍入到分后再相加。单价字段可有六位小数，因此差异不等于所有字段都只有两位精度。
- 判定舍入差时同时看计划级行金额与总计：区分每行按分舍入产生的差额，以及先汇总三位小数再取分与逐行取分后汇总之间的差额。若业务接受这类精度差，记录并说明即可；不要为了抹平几分钱而改动真实计划单价。
- 已验证例：AP00158171 的 TX082431，数量 118、含税单价 0.667；对账行是 78.706，金蝶未税单价 0.590265、未税金额 69.65、税额 9.05、含税金额 78.70。差 0.01 来自未税金额/税额分项舍入，与直接按含税单价乘数量的口径不同。

## 当期暂估与跨月财务应付的分支

2026-10-23 外协厂Y66行财务草稿改价验证：AP00165021（404594，供应商仍为G049）按原始对账逐计划修改含税价，63行使用对账价，TX0904824、TX0904883以79条匹配60元，调平价0.759494；TX0905067以199条匹配70.04元，调平价0.351960。66行金额逐条相等，合计5684.14→4987.20元，数量与来源主键未变，保持类型3草稿。证据 `output/yangni66-price/before.json`、`price-plan.json`、`after.json`、`verified.json`。本次Save会同步更新 `FEntityDetail_Link.FALLAMOUNTFOR_D` 为当前分录金额；不得把金额同步误判为来源关系变更，应单独核对链接其余字段（来源FID/分录ID、数量等）不变且链接金额正确。首次全对象链接比较误报后只读复查，未重试保存；未执行转销、提交或审核。该同步行为为本次单据实测，其他场景仍须读取实际结果验证。

业务口径来自用户明确纠正：本项目外发上锡对账中，已审核的暂估应付代表跨月，应到对应财务应付里改单价。此为项目业务约定，不是从状态 C 推导出的通用金蝶规则。

- 查询先区分 `FSETACCOUNTTYPE=2` 暂估与 `FSETACCOUNTTYPE=3` 财务应付，并核对期间、供应商、工序计划号和来源/下游关联。不得只看到已审核就提议反审核、删除、重建。
- 用户按“某月份的单”限定外发对账改价范围时，按来源工序结算/暂估的业务期间判定；不得仅按汇总财务应付表头日期归月。2026-10-23 用户纠正并经 WebAPI 验证：TX085171 来源暂估 AP00157328/结算 GXJGJSD103946 为9月28日，TX0900800 来源暂估 AP00152746/结算 GXJGJSD099872 为9月12日；两者财务应付虽然均为10月1日，仍属此次9月业务，不列为10月待办，也不要求为本次改价撤回。原先159条按财务应付日期统计的口径已纠正为157条10月来源；157条已修改计划的来源结算均重新验证为10月。证据：`output/xinyang-20261023-price-update/period-readback.json`、`changed-period-check.json`；复用前实时重查。
- 当期草稿暂估：仅在对应删除范围已获授权时，删除该暂估、反审核结算、改合格含税单价后保存；系统自动下推，只回查，不手动 Push。
- 跨月已审核暂估：保留已审核暂估和原结算链，先定位其对应财务应付的真实 `FID/FEntryID`；按用户明确对象和目标价仅修改对应财务应付。定位不到财务应付时继续只读调查，不用反审核旧暂估兜底。
- 财务应付修改按下文“直接改现有草稿 AP”模型，仅 Save、数量不动、非目标分录不动、保存后保持草稿。若目标财务应付自身已审核，先报告当前状态，不能把跨月约定当成反审核它的授权。
- 用户说“等下/不用了”时停止业务写入；这不阻止把已确认项目约定补入技能。

## 输出与写入边界

逐条报告至少包含：对账单总额、金蝶总额、单号缺失、对账单重复、数量差、单价/金额差、AP 多单、未匹配原因。建议同时输出 JSON（完整证据）和 CSV（业务复核）。

默认只读 dry-run。数量不默认修改；先按上面的当期/跨月分支确定修改对象。当期草稿暂估在用户确认采用删除重建流程时，顺序为：删除对应暂估应付单 → 反审核工序加工结算单 → 修改各计划的合格含税单价 → 保存结算单 → 由系统重新下推 AP → 回查新 AP 每计划数量、单价和金额。删除与反审核是写操作，执行前必须对当前精确对象重新查询，并取得本次范围的明确授权。类型3财务 `AP_PAYABLE` 只能保存草稿，禁止脚本 Submit、Audit 或启动工作流。

### 用户明确要求直接改现有草稿 AP 时

2026-10-23 外协厂X AP00165011 批量调平验证：用户授权排除TX085171，并仅将17个数量差计划按对账金额调平，金蝶数量不动。实时验证类型3草稿、763行，按当前全部763行复算确认13%分项舍入模型；17个目标金额按各计划对账三位金额四舍五入至分，六位含税价均可实现。一次最小 `FEntityDetail/FTaxPrice` Save 后，17行金额均精确达到分位目标、数量不变，746个非目标分录逐字段不变，单据仍为草稿。金额61113.20→61147.23元；排除旧账后原0.667对账组61147.892元，仍有0.662元差，不扩大为其他行调价。工作副本排除TX085197、TX0900800及TX085171；调平后以计划号而非继续筛0.667核对财务分录。证据 `output/xinyang-ap00165011-adjust/before.json`、`price-plan.json`、`after.json`、`verified.json`；本条仅为当次验证，其他单据须重新预检。

这与上面的“改工序结算单后重新下推”是不同路径；只有用户点名具体草稿 AP 并明确要求改该应付单时才用：

1. 重新查询该 AP 的 `FID`、供应商、状态、表头金额和全部分录；确认状态为草稿 `A`，按真实 `FEntryID` 唯一匹配工序计划号，保留非目标行和数量。
2. `View` 返回的读取集合名是 `AP_PAYABLEENTRY`，但本账套 `AP_PAYABLE` 的 Save 分录实体键经 `T_META_OBJECTTYPE.FKERNELXML` 验证为 `FEntityDetail`。最小更新模型形如 `{ FID, FEntityDetail: [{ FEntryID, FTaxPrice }] }`，`NeedUpDateFields` 使用 `['FTaxPrice']`，`IsDeleteEntry=false`。
3. 只调用 `DynamicFormService.Save`。即使响应 `IsSuccess=true`，也必须重新 `View` 并核对每个目标分录的 `TaxPrice`、`FALLAMOUNTFOR_D`、数量、非目标行和草稿状态；本次实测把 `AP_PAYABLEENTRY` 或 `FEntity` 当 Save 实体键均返回成功但字段未落地，改用 `FEntityDetail` 后才保存成功。禁止 Submit、Audit 或工作流。

## 保存结算单自动生成应付的验证流程

用户明确说明“改价后保存即可，系统自动下推”时，保存后只查询自动生成的 AP，不再调用 Push。没有新 AP、出现重复、价量异常时立即停止后续单据，先查保存响应和当前单据；不能用手动 Push 兜底。

外协厂Y改价实测验证：结算单 Save 最小模型为 `{ FID, FEntity: [{ FEntryID, FQualifiedTaxPrice: 目标价 }] }`，`NeedUpDateFields=[]`、`IsDeleteEntry=false`。此前使用 `FENTITY` 与 `NeedUpDateFields=['FENTITY.FQualifiedTaxPrice']` 返回成功但价格未落地，且系统仍生成原价 AP。不要只凭保存成功继续执行。

每张执行前查当前结算单和 AP 的供应商、计划号、来源、真实分录键、状态、价格与数量，并用 View 排除多分录和作废单。删除已授权草稿暂估 AP，反审核结算单，保存合格含税价后：

1. 回查 `FQualifiedTaxPrice`、`FBalanceTaxPrice` 均为目标价，合格数量和结算数量均不变。
2. 按供应商和来源结算单号查自动生成 AP；必须只有一张，价格正确、数量不变、状态为草稿 A。
3. 记录旧 AP、新 AP、结算单和计划号，并停止于任何不确定结果。字段未落地只允许重新预检后的一次受控重试，不能扩大范围。

## 前端六位单价显示与换算误差

用户要求统一显示单价时，不能只用 `abs(价格-目标)<1e-6` 判定已匹配；应另查前端六位显示值（如 0.7500005402 显示为 0.750001）。已验证 TX0900840：合格含税价本来为 0.75，结算含税价因换算为 0.7500005402，传递到草稿暂估 AP00154354。对已授权草稿 AP 用 `FEntityDetail/FTaxPrice` 最小 Save 精确设为 0.75 后，数量 1、金额 0.75、草稿状态均保持。结算换算值不因此改变，后续重生成 AP 仍须回查；不得承诺重存合格价必能消除派生误差。

## 暂估下推财务应付：草稿来源被过滤

已下推来源也须排除，不能把本张财务应付缺行一概归因于草稿过滤。2026-10-23 外协厂X0.667范围实时查得766条暂估，AP00165011为763分录草稿；另外三条的真实来源链接已在旧财务应付中：AP00157329/689023（TX085197、117片）→AP00158171/690302，AP00157779/689672（TX085197、4片）→AP00158172/705742，AP00152746/672909（TX0900800、95片）→AP00158172/691092。按来源FID/分录ID核实763+3完整覆盖后，不能再补推这三条。证据 `output/xinyang-ap00165011/target.json`、`scope-current.json`、`existing-financial-links.json`；仅为当次范围，复用前重查。
