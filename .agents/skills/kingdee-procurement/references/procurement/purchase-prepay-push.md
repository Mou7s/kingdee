# 采购订单下推付款申请（预付）失败排查

## 报错特征（前端下推时）

```
不符合下推条件
需要满足如下条件：
1. 单据已审核
2. 分期付款中包含预付
3. 分期付款中应付金额减去实付金额减去关联付款申请金额大于0
4. 分期付款中数量减去实际付款数量减去关联付款申请数量大于等于0
5. 采购订单不是变更中
取数失败原因分析：
- 是否预付 等于 是（不满足）
- 应付金额减去实际预付金额减去付款申请关联金额大于0，且采购订单不是变更中（不满足）
```

## 根因

`PUR_PurchaseOrder.View.FIinstallment` 为空（0 行）即没有付款计划，转换规则直接筛掉。
已审核（`DocumentStatus=C`）只是条件之一，不能单独证明可下推。

## 只读诊断（2026-09-03 实证）

```js
const v = await c.viewBill('PUR_PurchaseOrder', fid);
console.log(v.FIinstallment?.length); // 0 = 必失败；>=1 再看 ISPREPAYMENT
```

- 失败例：`TK20260815001`（FID 116185）`FIinstallment len=0`，收料/入库/开票全 0。
- 对照例：同供应商 `TK20260826008`（FID 116523）`FIinstallment len=1`，
  `ISPREPAYMENT=true`、`YFAMOUNT=1020`、`APPLYAMOUNT=1020`，可下推。
- 找对照单时用同供应商已下推成功的 PO，不要跨供应商猜模板。

## 处置方向

- 0 行 + 要预付：前端打开 PO → `付款计划`页签 → 补一行预付（金额/比例按业务确认），已审核单需先反审核再改，改后重审。
- 0 行 + 非预付（到货后付款）：不要硬下推付款申请，走正常链 `收料 → 入库 → 应付 → 付款申请 → 付款`。
- 补行前先让用户确认预付金额是全额还是部分（如 4×330=1320 全预付还是按比例），不代猜。
- 写操作（反审核/Save/审核）属受控写入，仅在用户明确授权该单后执行。
